## 3. Лимит размера фото + обработчик ресайза изображений

**Контекст.** 2026-06-13 при автопостинге в Telegram всплыло: бот отправлял фото
по URL, а Telegram сам качает картинку и **отвергает оригиналы тяжелее ~5 МБ**
(лимит «по ссылке»). Сделаны два обходных шага: (1) бот шлёт фото файлом
(`URLInputFile`, потолок 10 МБ); (2) когда фото — наш локальный `/uploads/...`,
воркер читает файл **прямо с диска** (`FSInputFile` в `channel_publisher._photo_input`),
не завися от сетевой доступности URL из воркера. Это **костыли под один VPS**, а
не решение корня.

**Корень проблемы:**

- `backend/app/api/v1/uploads.py` сохраняет **только полноразмерный оригинал** —
  `original_url == thumbnail_url == medium_url == large_url` указывают на один и
  тот же файл (есть комментарий «no image processing»). Принимаем до 10 МБ
  (`MAX_FILE_SIZE = 10 * 1024 * 1024`).
- Уменьшенных рендишенов нет нигде → и в карточках, и в канале грузится тяжёлый
  оригинал (трафик, скорость, риск упереться в лимиты Telegram по размеру/размеру
  сторон — до 10000 px суммарно даже при загрузке файлом).

**Индустриальный стандарт (целевая архитектура):**

- **Объектное хранилище** (S3 / GCS / self-hosted MinIO) вместо локального диска
  — стабильные публичные URL, доступные браузеру, Telegram и любому воркеру; нет
  привязки к тому конкретного контейнера (текущая боль). В конфиге уже есть
  заготовки (`cloudfront_domain`, AWS S3) — направление выбрано, не подключено.
- **CDN** перед хранилищем (CloudFront / Cloudflare / Fastly) — кешируемая
  публичная раздача с корректными заголовками.
- **Пайплайн рендишенов** на загрузке (libvips/`pyvips` или Pillow; либо
  on-the-fly imgproxy / Thumbor / Cloudinary): несколько размеров + WebP/AVIF,
  срезка EXIF, ограничение размера/качества. Поля `thumbnail/medium/large_url`
  у `ListingImage` под это уже есть — сейчас все указывают на оригинал.
- **Telegram-специфика:** слать ограниченный рендишен (`large`), а после первой
  отправки сохранять возвращённый **`file_id`** и переиспользовать при повторных
  постах/правках (не загружать файл заново).

**Что сделать:**

1. **Отрегулировать максимальный размер фото** на загрузке — определить разумный
   потолок (вес и/или разрешение) и валидацию на бэке + фронте.
2. **Написать обработчик ресайза** (например, Pillow): при загрузке генерировать
   несколько рендишенов (`thumbnail` / `medium` / `large`) и заполнять
   соответствующие поля `ListingImage`, а не дублировать оригинал.
3. Автопостинг и карточки переключить на подходящий рендишен (например,
   `large_url`) вместо `original_url`.
4. Бэкофилл для уже загруженных изображений (по желанию).

**Открытые вопросы:**

- хранение: остаёмся на локальном диске (`/uploads`) или переезд на S3/MinIO
  (в конфиге есть заготовка под AWS S3);
- целевые размеры рендишенов и качество JPEG;
- нужен ли асинхронный (Celery) ресайз, чтобы не тормозить загрузку.

**Когда возвращаемся:** после стабилизации автопостинга; текущие костыли
(`URLInputFile` + чтение фото с диска `FSInputFile`) закрывают боль до этого
момента.

## 4. Единый источник данных для бота и приложения (нормализация выдачи)

**Контекст.** 2026-06-15. И лента приложения, и бот (inline / `/search`) читают
объявления из ТРЁХ разных таблиц и приводят их к «общему виду» **на лету**,
причём **двумя независимыми кусками кода**:

- `listings` — нативные (есть `title`, `description`, структурные поля);
- `telegram_listings` / `olx_listings` — спарсенные: парсер (LLM) раскладывает
  сырой текст по структурным полям (`rooms`, `price`, `district`, `area_sqm`,
  `description`, `raw_text`…), но **поля `title` у них НЕТ**;
- приложение собирает выдачу через `_telegram_listing_to_unified` /
  `_olx_listing_to_unified` (`api/v1/listings.py`), бот — через
  `services/bot_search.py` (`_crawled_to_result` / `_native_to_result`).

Спарсенная строка попадает в `listings` только при **claim** продавцом
(`converted_listing_id`); до этого живёт в своей таблице. Единого
«обработанного» представления, из которого читают ВСЕ, **нет**.

**Проблемы:**

- **Дублирование** логики нормализации (две реализации) → расходятся.
- У спарсенных **нет заголовка** → и бот, и лента **синтезируют** его из
  `rooms/district/price` каждый по-своему (см. `inline.py::_format_card_text`).
- Трудно гарантировать, что бот и приложение показывают одно и то же.

**Варианты решения:**

- **A. Общий слой нормализации (дёшево, без смены схемы).** Один модуль
  «строка любого источника → канонический DTO» (с готовым `title` / `description`),
  который используют И бот, И лента. Туда же — единая генерация «человеческого
  заголовка» для спарсенных (тип жилья + комнаты + район). Убирает дублирование
  и расхождения. `bot_search` и фид переключить на него.
- **B. Готовые поля при записи / нормализованное представление (чище, дороже).**
  Генерировать клиентские поля (включая `title`) на этапе парсинга и
  **сохранять** (новые колонки в crawled-таблицах либо единая таблица/`VIEW`).
  Все читают готовое поле, ничего не вычисляя на лету. Нужны миграция + бэкофилл.
- **Рекомендация:** **A сейчас** (быстро снимает расхождения), **B позже** (при
  полноценной нормализации / генерации заголовков и переходе на S3/CDN из п.3).

**Что сделать (для A):**

1. Завести единый канонический DTO + `native_to_canonical` /
   `telegram_to_canonical` / `olx_to_canonical` в одном месте
   (напр. `services/listing_normalize.py`).
2. Туда же — единая функция «человеческого заголовка» для строк без `title`.
3. Переключить `bot_search` и фид (`listings.py`) на общий слой.
4. Тесты на маппинг полей и генерацию заголовка (ru/uz).

**Открытые вопросы:**

- где живёт канонический слой и его DTO;
- шаблон «человеческого заголовка» и язык (ru/uz);
- генерируем ли заголовок и для нативных без `title`.

**Ключевые файлы:**

- `backend/app/services/bot_search.py` (`_native_to_result`, `_crawled_to_result`)
- `backend/app/api/v1/listings.py` (`_telegram_listing_to_unified`,
  `_olx_listing_to_unified`, фид)
- `backend/app/bot/inline.py` (`_format_card_text` / `_format_card_html`)
- `backend/app/db/models.py` (`Listing`, `TelegramListing`, `OLXListing`)
