## 3. Лимит размера фото + обработчик ресайза изображений

**Контекст.** 2026-06-13 при автопостинге в Telegram всплыло: бот отправлял фото
по URL, а Telegram сам качает картинку и **отвергает оригиналы тяжелее ~5 МБ**
(лимит «по ссылке»). Сделаны два обходных шага: (1) бот шлёт фото файлом
(`URLInputFile`, потолок 10 МБ); (2) когда фото — наш локальный `/uploads/...`,
воркер читает файл **прямо с диска** (`FSInputFile` в `channel_publisher._photo_input`),
не завися от сетевой доступности URL из воркера. Это **костыли под один VPS**, а
не решение корня.

**Корень проблемы:**

- `backend/app/api/v1/uploads.py` сохраняет **только полноразмерный оригинал** —
  `original_url == thumbnail_url == medium_url == large_url` указывают на один и
  тот же файл (есть комментарий «no image processing»). Принимаем до 10 МБ
  (`MAX_FILE_SIZE = 10 * 1024 * 1024`).
- Уменьшенных рендишенов нет нигде → и в карточках, и в канале грузится тяжёлый
  оригинал (трафик, скорость, риск упереться в лимиты Telegram по размеру/размеру
  сторон — до 10000 px суммарно даже при загрузке файлом).

**Индустриальный стандарт (целевая архитектура):**

- **Объектное хранилище** (S3 / GCS / self-hosted MinIO) вместо локального диска
  — стабильные публичные URL, доступные браузеру, Telegram и любому воркеру; нет
  привязки к тому конкретного контейнера (текущая боль). В конфиге уже есть
  заготовки (`cloudfront_domain`, AWS S3) — направление выбрано, не подключено.
- **CDN** перед хранилищем (CloudFront / Cloudflare / Fastly) — кешируемая
  публичная раздача с корректными заголовками.
- **Пайплайн рендишенов** на загрузке (libvips/`pyvips` или Pillow; либо
  on-the-fly imgproxy / Thumbor / Cloudinary): несколько размеров + WebP/AVIF,
  срезка EXIF, ограничение размера/качества. Поля `thumbnail/medium/large_url`
  у `ListingImage` под это уже есть — сейчас все указывают на оригинал.
- **Telegram-специфика:** слать ограниченный рендишен (`large`), а после первой
  отправки сохранять возвращённый **`file_id`** и переиспользовать при повторных
  постах/правках (не загружать файл заново).

**Что сделать:**

1. **Отрегулировать максимальный размер фото** на загрузке — определить разумный
   потолок (вес и/или разрешение) и валидацию на бэке + фронте.
2. **Написать обработчик ресайза** (например, Pillow): при загрузке генерировать
   несколько рендишенов (`thumbnail` / `medium` / `large`) и заполнять
   соответствующие поля `ListingImage`, а не дублировать оригинал.
3. Автопостинг и карточки переключить на подходящий рендишен (например,
   `large_url`) вместо `original_url`.
4. Бэкофилл для уже загруженных изображений (по желанию).

**Открытые вопросы:**

- хранение: остаёмся на локальном диске (`/uploads`) или переезд на S3/MinIO
  (в конфиге есть заготовка под AWS S3);
- целевые размеры рендишенов и качество JPEG;
- нужен ли асинхронный (Celery) ресайз, чтобы не тормозить загрузку.

**Когда возвращаемся:** после стабилизации автопостинга; текущие костыли
(`URLInputFile` + чтение фото с диска `FSInputFile`) закрывают боль до этого
момента.
